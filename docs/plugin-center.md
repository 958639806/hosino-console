# 原生插件中心

入口：**更多 → 能力与任务 → 插件中心**。原有“插件与技能”状态页保留，可从该页进入中心。

插件运行在已有 OpenClaw 中，QQ 仍由原 QQ 插件接入。控制台增加管理界面和 REST 接口，不引入 AstrBot 服务、Python 兼容层或额外常驻进程。后续选定其他生态的插件时，先将业务功能重写为 OpenClaw 原生扩展，再验证并接入。

## 首版能力

- 搜索、筛选已发现的原生插件，查看版本、来源、启用和运行状态、受保护原因及安全处理后的错误。
- 查看插件详情、声明的组件、配置规范和当前配置；凭据只展示已设置状态。
- 按配置规范编辑，查看实际字段差异，复制或下载变更单。
- 根据实时能力区分可直接应用与需要维护处理的变更。未应用的预览不宣称已经保存或生效。
- 为以后经过审核的原生插件保留受限制的配置应用路径；默认不对第三方插件开放直接应用。

现有插件状态页、技能详情、聊天、文件编辑器、模型和 xAI 检测流程保持原样。新分区按需加载，不增加后台常驻轮询。

## 为什么安装和启停不直接执行

核对 `openclaw@2026.9.8` 发布源码后确认：

1. `plugins.install`、`plugins.setEnabled`、`plugins.uninstall` 等生命周期 RPC 没有通用的 `dryRun` 或 `noRestart` 参数。`restartRequired` 是执行之后的结果，不能用它实现写入之前的阻止。
2. 即便变更的不是 QQ 插件，命令注册集合变化也可能使已有渠道执行停止和启动，影响 QQ 连接。
3. 安装时的 `enable:false` 保留已有启用策略，并不保证新包及其子插件全部保持停用。
4. 启用新的槽位插件可能替换当前 memory/context-engine 槽位；同包操作也可能影响其他成员。

因此首版的生命周期变更用于预览和生成维护变更单，不调用上述写 RPC。界面不提供假装可以安全执行的安装、更新或启停按钮。未来真正开放前，需要针对所选原生插件核验包成员、槽位、渠道和命令影响，并安排相应维护流程。

配置应用同样默认关闭。只有代码审核名单中的插件，同时满足实时规则明确无需重载、配置规范有效、未触及受保护组件等条件，才能提供确认应用；首版生产集成的审核名单为空。

## 配置与凭据

- 仅允许当前插件的 `plugins.entries.<id>.config` 命名空间，不允许借配置表单修改槽位、插件启用状态、QQ 或网关配置。
- 不返回旧凭据原值，不把隐藏占位符当作新值写回。预览和导出也清除敏感值。
- 应用必须确认，并核对配置版本、当前配置规范、保护状态及生效规则。静默窗口只允许读取和预览。
- QQ、memory/context-engine 槽位、本地守卫和受保护插件的同包成员均受到保护；未知影响不当作安全证明。
- 操作错误使用受控提示，审计不保存配置正文或凭据。

## 未来插件接入

1. 明确功能、触发方式、平台能力和所需数据。
2. 将命令、消息、配置、存储和任务生命周期接入 OpenClaw；复用可用的业务规则、题库和素材。
3. 使用真实原生插件清单与配置规范，补齐消息去重、权限、会话隔离和故障测试。
4. 本地验证后，在插件中心查看能力与变更预览，再确定部署和维护步骤。

重写可以减少框架之间的适配负担，但兼容性仍以逐项测试为依据。
