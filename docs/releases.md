# 发布、升级与回滚

## 不覆盖旧版本

每次修复发布使用新的版本号、Git 标签和版本包文件名。保留历史提交、标签、Release 和附件；不要移动旧标签、强制推送或用同名附件覆盖旧包。本次新版本为 `v2026.11.4`，实际发布状态以 GitHub 为准；`v2026.11.3.7` 快照、`v2026.11.3`、`v2026.11.2` 均保留，最早源码基线为 `1bcb35f928ad6f0ce46b32d38bccacea255ef170`。

版本说明必须包含本次具体修复、兼容性变化、验证结果及未验证的外部集成。`CHANGELOG.md` 是仓库内的逐项记录。

`v2026.11.4` 的定制包包含根运行模块、public、依赖锁、mock、当前 tests、文档和当前语音参数测试；不包含 node_modules、凭据、运行数据、旧 staging 快照或展示截图。完整 Git 历史和历史开发材料仍由仓库及 GitHub 自动源码归档保留。定制 tar.gz/zip 及 SHA256SUMS 使用版本专属文件名。

## 独立目录部署

发布源码不自动修改生产服务。需要部署时，先确定目标主机、服务启动方式、配置路径和当前运行版本，再执行以下流程：

1. 将新版本解压到新的独立目录，例如 `releases/<新版本号>`，不要在旧版本目录内解压。确认版本包校验值。
2. 在新目录执行 `npm ci --omit=dev`。使用独立、安全的环境文件和网关证书，保持 TLS 校验开启。
3. 备份旧版运行数据和配置。后端的 `data/`、`logs/`、`backups/` 路径相对于当前 `server.mjs` 所在目录；升级时必须明确迁移或共享它们，不能把新目录默认空数据当作原来的数据。不要把运行数据和凭据放进版本包。
4. 使用独立测试端口验收登录、网关连接、QQ 收发、群报和原生 CLI。离线回归通过不能替代这些真实集成验收。测试群报时避免重复投递。
5. 验收后再调整服务启动目标，记录切换前后路径和版本，重启并检查健康情况。不要删除旧目录或旧包。

## 回滚

恢复服务原来的启动目录和配置，重启并验证。保留升级前的数据快照以便比较；不要直接覆盖升级后产生的新消息或新数据。

回滚应恢复目标版本完整文件与匹配的依赖，而非只替换 `server.mjs`。例如 `v2026.11.3` 不包含 `chat-actions.mjs`；应使用该标签的完整源码与锁文件，不应要求从旧标签取不存在的文件。新功能模块不可与旧后端任意混装。

配置、密钥和 OAuth 账号保存在外部网关。代码回滚不会撤销白名单写入、恢复旧密钥、撤销已完成的授权或还原账号顺序；需在切换前另行记录配置版本及恢复方案，密钥保持只写不读。控制台不会自动撤销已完成授权。

v2026.11.3 能读取旧群报图片，但 v2026.11.2 不能完整识别新版不可变图片文件名与强制重发批次。因此回滚不能只换代码后继续投递新版群报：应暂停投递，保留升级后数据副本，再恢复匹配旧版的升级前数据快照并核对已发送记录，避免丢失新数据或重复发送。回滚也会重新引入旧版已知缺陷。

## 发布前检查

- `npm ci` 和 `npm test` 成功。
- 当前后端语音参数测试成功，历史 fixture 测试与当前版本测试分别记录。
- 资源查询版本已更新，避免浏览器继续使用旧 JS/CSS。
- `package.json`、Git 标签和 Release 说明中的版本一致。
- 新版本包和校验文件采用新名字；检查已有标签和发布，发现同名即停止，不能覆盖。
- 保留旧版源码基线及其校验值，Release 中列出未进行的生产验收。
